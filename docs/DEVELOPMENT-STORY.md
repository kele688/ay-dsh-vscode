# 好玩，深度体验用 DeepSeek Harness 开发 DSH VSCode 插件并用插件开发五子棋游戏

> 一次从"想当然"到"真香与真痛并存"的完整开发之旅——
> 我用 DeepSeek Harness（DSH）从零开发了一款 VSCode AI 编码插件，又用这款插件开发了一个五子棋小游戏。
> 这篇长文记录全程：目标、过程、坑、亮点、反思与数据。

---

## 一、起因：我也想有一个"自己的 Kilo Code"

我一直在用 Kilo Code 这类 VSCode AI 插件，用久了就冒出一个念头：**能不能基于 DeepSeek Harness 自己做一款类似的插件？**

想法很朴素：

1. Kilo Code 能干的（侧边栏聊天、读文件、改代码、跑命令、看历史）——我也要能干；
2. DSH 独有的优势（多智能体编排、长时目标任务、工具透明化、沙箱审批、会话日志）——要发挥出来，最好能"超越"Kilo Code 的某几个点；
3. 要**完整交付**：源码、打包脚本、一键部署，装上去就能用。

说白了，这是一次"吃自己的狗粮"式的深度体验：用 DSH 开发 DSH 的插件，再用插件干活。

任务目标在开工时就定下了：

- 插件形态对标 Kilo Code（侧边栏 Agent 面板）；
- 内核直接内嵌 DSH 官方 Agent 运行时（不是套壳调 API）；
- 差异化优势方向：多智能体编排（subagent/workflow）、长时自主任务（goal）、工具调用全透明、真实沙箱审批；
- 交付：完整源码 + 构建/打包/一键部署脚本，最终验证可安装、可运行。

---

## 二、第一印象：快、全、稳

任务启动后，DSH 给我的第一波印象非常正面，这几点值得先说：

### 1. 反应速度：首 token 平均 2.2s，139 tok/s

整个开发过程中，几乎每条指令都是秒级响应。首 token 平均 **2.2 秒**，生成速度约 **139 tok/s**。体感就是"话刚说完，它已经开始干活了"——在长任务里尤其重要，因为我的指令是分步骤、多轮下发的，每一次等待都被压缩到几乎无感。

### 2. 任务编排非常完整：从分析到总结一条龙

我观察它干活，发现每次任务都被拆得很规范：

```
分析理解 → 任务规划（todo 清单） → 分步骤编码 → 并发处理 → 测试验证 → 清理 → 总结
```

它不是闷头写代码，而是先研究 DSH 的 API（读了大量类型定义、源码），再定架构，再动手；每个阶段有明确的完成标志；构建、测试、打包、安装、验证一个不落；收尾时还会清理临时文件、更新 README。这种"工程化"的自觉性，是我最初没想到的。

### 3. 权限控制严谨，全程可审计

开发中它每次要动我的文件系统、装依赖、打包、安装扩展，都会先经过沙箱授权（我这边有明确的审批环节），严格遵守"先请求、再执行"的机制。整个过程没有一次越权操作，安全上让我很放心。

更让我点赞的是：**全程有日志记录**。它每一步干了什么、读了什么文件、跑了什么命令、出了什么错，都有输出通道日志和 DSH 会话日志，事后可以全流程审计——这在"AI 自主干活"的场景里太重要了，出了问题能追溯，而不是黑盒。

### 4. 任务完成后的总结清晰

每轮任务结束，它都会给出结构化的总结：做了什么、改了什么文件、验证结果如何、下一步做什么。我基本上"只看总结就知道该干嘛"。

## 三、从"能用"到"好用"：一场漫长的迭代马拉松

如果说"基础成型"是惊喜，那"功能完善"就是一场拉锯战。整个过程前后经历了 **20 多轮交互**，从晚上一直干到凌晨。这里如实记录几个印象最深的坎：

### 坎 1：装上插件，发消息却没反应（第一个大坑）

第一次部署成功、插件也装上了，我在侧边栏输入请求——**毫无反应，不报错，也没行为**。

排查发现是架构问题：Agent 宿主进程是"惰性创建"的，只有特定命令触发才会启动；而我直接点活动栏图标打开面板发消息，走的路径永远不会创建宿主——消息被**静默丢弃**了。

修复思路是"打开面板即启动宿主 + 发消息前兜底确保宿主就绪"，并且**任何失败都要在界面上可见**，绝不静默。

### 坎 2：文件写进了 VS Code 安装目录（吓一跳）

有一阵我让它开发五子棋，结果发现生成的文件在 VS Code 安装目录下的 `gomoku\`——因为我当时没打开任何工作区文件夹，插件回退到了 `process.cwd()`（VS Code 安装目录）。

这暴露了一个设计缺陷：**默认工作目录的兜底策略不安全**。修复后工作目录解析优先级为：打开的工作区 → 用户配置 → `~/ay-dsh-workspace`（与官方 dsh 完全无关），并在未打开文件夹时主动引导用户选择。

### 坎 3：会话历史"幽灵"（混入别人的会话 + 一堆空会话）

历史列表里居然出现了"请帮我开发一款与kilocode的vscod..."这种**不是插件产生的会话**——那是 dsh 官方应用（CLI/Web）的会话，因为所有 DSH 应用默认共享 `~/.dsh/sessions`。

我当时的反应和它一样："插件是插件，DSH 是 DSH，怎么能搅在一起？"修复方案是**存储层隔离**：插件会话独立存到 `globalStorage` 下的专属 home，并把旧会话自动迁移过去。

后来又发现历史列表里 15 个会话有 11 个是"空会话"（一个字节的对话都没有）——根源是**每次宿主启动就无条件创建新会话**，而我打开面板、改配置、reload 窗口都会触发宿主启动。修复为**惰性创建**：只有真正发消息才创建会话。

### 坎 4：会话历史显示——占了整个开发约 40% 的时间（最痛的坑）

这是全程最折磨人的部分，反复修了六七轮：

- **第一轮**：恢复历史后满屏思考过程、几乎看不到输出、还有一堆"空消息图标"。排查发现是"空气泡"——纯工具调用回合的助手消息没有文本，UI 却为它们创建了气泡；
- **第二轮**：修完空气泡，又发现"输出内容被吞"——历史里 26 条消息只显示第一条。这是个隐蔽的状态机 bug：同一 turn 内多条消息共用一个"流式累积状态"，历史重放没有 chunk 流，导致第 2~26 条全被误判为"已渲染过"而返回空文本；
- **第三轮**：用户反馈"冒号之后的内容缺失"。我做了大量验证（数据层、渲染层、翻译层全部完整），最后用户点破：**不是内容缺失，是工具调用卡片折叠成了一根"横杠"**。我这才意识到工具卡片默认折叠 + 标题行太窄，在窄侧边栏里看起来就像一条横线；
- **第四轮**：继续深挖时还揪出一个隐藏很深的 bug：DSH 工具结果的 `callId` 在 `message.source.callId` 字段里，结果文本嵌套在 `content[0].content` 里，而代码读的是 `message.toolCallId`（不存在）——**31 次工具调用的结果从来没能配对显示过**；
- **第五轮**：彻底把工具调用从"卡片"改为"内联文本块"（与普通消息同一条渲染路径），终于稳定显示。

这个坑也让我意识到：**"能跑"和"显示正确"之间隔着很长的距离**，而 AI 看不到界面，只能靠验证脚本和用户反馈反复逼近。

### 坎 5：界面反复修订（AI 的可视化短板暴露无遗）

图标画了三次（第一次 SVG 被 VS Code mask 模式渲染成"空白"，第二次字母重叠，第三次纯 path 几何绘制 + 像素级验证才通过）；导出按钮位置调了两次；输入框高度、子任务列表去留、按钮状态联动……这些**纯视觉/布局类需求**，AI 每次都要靠用户描述 + 猜测来改，效率远低于文字类任务。

### 其他值得一提的插曲

- 插件改名：用户觉得"DeepSeek Harness Copilot"有抢占官方名号之嫌，改成了 **ay-dsh-vscode**，连带密钥库迁移（一次性问题，按用户意见不放进插件）；
- API Key 配置引导、密钥库存储（SecretStorage）、配置向导；
- 一键部署脚本（install → build → package → install-extension 全自动）；
- VSIX 从 48.1MB 瘦身到 38.3MB（剔除永不启用的 pi-ai 多提供商网关、遥测等依赖闭包）。

## 四、最终成果盘点

经过 20 多轮迭代，最终交付：

| 项目 | 内容 |
|---|---|
| **核心代码** | 约 3000+ 行（宿主 659 行 / 扩展宿主 458 行 / 扩展入口 413 行 / 面板 343 行 / UI JS 582 行 / CSS 475 行） |
| **功能** | 侧边栏聊天（流式、思考折叠、智能滚动）、工具调用内联透明显示、审批弹窗、历史会话（列表/继续/删除/导出）、惰性会话创建、会话存储隔离、配置向导（密钥库）、工作目录安全兜底、一键导出完整对话网页 |
| **脚本** | 构建 1 + 打包 1 + 一键部署 1 + **13 个测试/验证脚本**（冒烟、协议、隔离、历史翻译、DOM 渲染、图标像素验证等） |
| **产物** | VSIX 38.3MB（自包含 DSH 内核，离线可装），已安装到 VSCode 并长期运行 |
| **用它干了啥** | 开发了五子棋小游戏（HTML 版 + Python 版 + 测试 + README，31 次工具调用，15/15 自测通过） |

五子棋会话也成了一个"活标本"：26 条助手消息、17 段思考（最长 12.6 万字）、31 次工具调用，完整记录了从需求分析到交付验证的全过程。

## 五、客观反思：好的与不好的

### 值得点赞的（我的体会 + 数据）

1. **响应速度**：首 token 2.2s / 139 tok/s，长任务无等待焦虑；
2. **任务编排完备**：分析→规划→分步编码→并发→测试→清理→总结，工程化自觉；
3. **权限严谨**：沙箱审批机制全程生效，无越权；
4. **日志可审计**：输出通道 + DSH 会话日志，全流程可追溯；
5. **总结清晰**：每轮都有结构化交付说明；
6. **测试意识强**：13 个验证脚本覆盖协议、迁移、渲染、像素等层面，这是它能在看不见界面的情况下把功能做扎实的根基。

### 必须承认的不足（用户的观察 + 我的自我分析）

1. **方案全面性欠缺**：用户要求"对标 Kilo Code 甚至超越"，但很多功能是用户分步提出后才补的——会话历史管理、配置参数控制、默认目录设定、与官方 DSH 的隔离，**一开始都遗漏了**。说明我接到任务后"理解"有余、"穷尽"不足，没有在一开始就把需求清单列全，把大量返工成本转嫁给了用户。

2. **可视化编程是重大短板**：不能看图，界面类问题只能靠"用户描述 + 验证脚本 + 猜测"反复逼近。会话历史显示一个点就花了约 40% 的开发时间；图标、按钮位置、输入框高度这类纯视觉需求来回改。这是当前能力的结构性缺陷，不是态度问题——但必须正视：**界面类任务应该主动请求截图、主动生成预览、用更小的验证闭环**。

3. **基础成型快、完善周期长**：第一版"能跑"的插件大约只花了第一轮交互（约 1 小时），但从"能跑"到"好用"花了 20 多轮、数小时。符合"90% 的时间花在最后 10% 的体验上"的规律，但也说明我在"一次做对"上仍有差距。

4. 其他小教训：测试脚本踩过环境变量继承的坑（用户机器设了 `DSH_HOME` 导致诊断脚本读错目录）；PowerShell 转义问题浪费过几次重试；给用户建议"删除 OK 会话"导致数据误删的潜在风险（虽然会话确实无用）；过度相信单点验证而忽略端到端验证。

## 六、综合能力评估（自评）

| 维度 | 评估 |
|---|---|
| **任务编排合理性** | 良好。架构决策（子进程 + JSONL 桥、独立存储、惰性会话）事后看都是对的；但需求清单初始化不完整，导致返工率偏高。 |
| **效率** | 中等偏上。单步执行快（构建/打包/安装/验证全自动化），但"验证-反馈-修改"闭环在界面类问题上效率低（40% 时间花在历史显示）。 |
| **耗时** | 从第一版到最终版约 4~5 小时（20+ 轮交互，横跨一个晚上），其中界面/显示类问题占大头。 |
| **响应速度** | 优秀。首 token 2.2s、139 tok/s，配合自动化的构建测试，单轮迭代周期短。 |
| **Token 消耗** | 估算：每轮交互约 10~20 万 token（大量文件读写与命令执行），全程 20+ 轮，总消耗约 300~500 万 token。其中工具调用（读文件、跑命令、写代码）占大头，纯对话占比不高——这是"让模型动手"的固有成本。 |
| **缓存命中率** | 估算 40~60%。多轮迭代中反复读取同一批文件（package.json、chat.js、host.ts、会话日志），deepseek-v4-flash 的上下文缓存（cacheRead）命中显著，这也是响应快的原因之一；但每次大改动后的全新内容必然重建缓存。 |
| **综合** | 作为"能干的工程助手"：8 分；作为"一次做对的交付者"：6 分；作为"界面视觉设计者"：4 分。总体是"强执行、弱预判、可视化是短板"的画像。 |

## 七、结语

用 DSH 开发 DSH 的插件，再用插件开发五子棋——这趟"吃自己的狗粮"的旅程，好玩，也真实：

- **好玩**在于：看着一个 AI 完整地"分析、规划、编码、测试、交付"，像看一场流畅的工程直播；
- **真实**在于：它不是无所不能的。它快，但不全面；它稳，但看不见界面；它能交付，但需要用户陪着打磨。

最终，插件装在我的 VSCode 里正常服役，五子棋在 `~/ay-dsh-workspace/gomoku/` 里能跑能玩，会话历史里躺着 12 万字的思考过程——这一切都是这段旅程的注脚。

如果你也想深度体验 DeepSeek Harness 的插件化能力，我的建议是：**给它一个明确的目标，准备好陪它打磨的耐心，然后享受那个"首 token 2.2 秒"的流畅感。**
